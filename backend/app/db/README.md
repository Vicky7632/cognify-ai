# Database

`base.py` defines the shared SQLAlchemy declarative base. Models imported through `app.models` register their tables with `Base.metadata` without creating an engine or connecting to PostgreSQL.

`Document` in `app/models/document.py` describes the `documents` table with a UUID primary key, original filename, supported file type, local storage path, processing status, optional safe processing error code, and timezone-aware creation/update timestamps. Supported initial file types are PDF, TXT, MP3, WAV, and MP4. Metadata-only records default to legacy `pending`; actual uploads start as `uploaded`. Lifecycle statuses are `uploaded`, `processing`, `completed`, and `failed`, with `pending` retained for compatibility.

The UUID default is generated by SQLAlchemy when inserting through the ORM; it is not a PostgreSQL server default. `updated_at` has a database default for inserts and a SQLAlchemy `onupdate` expression for ORM updates, not a database trigger.

This is an ORM model definition, while schema creation and changes are managed separately through Alembic revisions in `backend/alembic/`. The initial migration has been applied to the configured local `cognify_ai` database. Do not use `Base.metadata.create_all()` for application schema changes.

`session.py` provides lazy PostgreSQL engine creation, a cached SQLAlchemy session factory, and the `get_db` FastAPI dependency. Configure the optional `DATABASE_URL` before a route requests a database session. Importing the application and using the health endpoint do not create an engine or require a database URL.

The yielded session is closed after request handling. Mutation routes own explicit transaction boundaries; service and repository methods do not commit or roll back.

## Document repository

`app/repositories/document_repository.py` provides create, get-by-ID, list, conditional status-transition, and delete operations using the caller-provided SQLAlchemy session. Listing is ordered by creation time descending, with UUID ascending as a deterministic tie-breaker. Missing documents return `None` for get/status-transition and `False` for delete. Status updates compare the expected current state to prevent stale transitions.

Repository operations flush changes but never commit or roll back. The caller owns the transaction and decides whether to commit or roll it back. Repository methods return ORM records for internal persistence use; public API schemas must not expose local storage paths.

`app/services/document_service.py` provides the corresponding document use cases, validates file types and lifecycle transitions, and delegates all persistence to the repository. It also leaves commit and rollback decisions to its caller.

## Migration workflow

Run commands from `backend/` with its virtual environment active. Alembic loads `DATABASE_URL` using the application settings and imports `app.models` to expose all model metadata for autogeneration:

```powershell
python -m alembic current
python -m alembic revision --autogenerate -m "describe schema change"
python -m alembic upgrade head
python -m alembic current
```

Before applying a revision, inspect the target database's existing tables and Alembic history using read-only queries, then review the complete revision for unintended changes. Apply revisions only to the intended local development database. Never use `stamp head` to bypass applying schema changes.
